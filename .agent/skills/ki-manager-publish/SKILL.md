# ki-manager: Публикация новой версии

## Overview

Скилл выполняет полный цикл релиза пакета `ki-manager` на PyPI через GitHub Actions:
- обновляет версию в двух файлах,
- создаёт git-коммит и тег,
- пушит тег на origin (GitHub Actions публикует пакет автоматически).

## Trigger phrases

Запускается при любом из этих запросов (или схожих по смыслу):
- «запушь новую версию»
- «создай версию пакета»
- «опубликуй релиз»
- «сделай релиз»

Если пользователь просит «сделай коммит» / «запушь изменения» **без упоминания версии** — ОБЯЗАТЕЛЬНО спроси:
> «Хочешь попутно выпустить новую версию пакета на PyPI или просто сделать коммит?»

## Workflow

### Шаг 0: Уточнение версии

Перед тем как что-либо менять:

1. Прочитай текущую версию из `pyproject.toml` (строка `version = "..."`).
2. Предложи следующую patch-версию (например `2.0.11` → `2.0.12`).
3. Спроси пользователя, подтверждает ли он эту версию или хочет указать другую.

> [!IMPORTANT]
> Не меняй версию без явного подтверждения пользователя.

### Шаг 0.5: Проверка актуальности метаданных для Smithery

Перед тем как публиковать новую версию, необходимо проверить, что описания инструментов в мета-файлах (`manifest.json` и `server-card.json`) полностью соответствуют реальному коду сервера:
1. Описания инструментов, их списки и `inputSchema` должны совпадать с тем, что сервер фактически отдает агентам.
2. Проверь код (например, `src/ki_manager/server.py` или списки инструментов) на предмет недавних изменений, чтобы убедиться, что витрина Smithery остается актуальной.

### Шаг 1: Проверить состояние репозитория

```powershell
git status
git log -n 3 --oneline
```

Убедись, что рабочая директория чистая или все нужные изменения добавлены. Если есть незакоммиченные файлы — спроси пользователя, добавлять ли их в этот релиз.

### Шаг 2: Запустить скрипт релиза

Для полной автоматизации используй встроенный скрипт `scripts/publish.py`.

Запусти скрипт из корневой папки репозитория (укажи путь к скрипту внутри папки скилла):

```powershell
.venv\Scripts\python.exe C:\Experiments\KI-base\.agent\skills\ki-manager-publish\scripts\publish.py X.Y.Z -m "Commit message here"
```

* `X.Y.Z` — это подтверждённая пользователем новая версия.
* Сообщение коммита по умолчанию (если не указывать `-m`): `"Bump version to X.Y.Z"`. Если пользователь указал своё сообщение, передай его через `-m`.

> [!NOTE]
> **Что происходит под капотом (для справки и отладки):**
> Скрипт `publish.py` автоматически выполняет следующие шаги:
> 1. Обновляет версию пакета в 5 файлах, которые должны быть синхронизированы:
>    - `pyproject.toml` (`[project] version = "..."`)
>    - `src/ki_manager/__init__.py` (`__version__ = "..."`)
>    - `smithery.yaml` (`version: "..."`)
>    - `.well-known/mcp/server-card.json` (`"version": "..."`)
>    - `manifest.json` (`"version": "..."`)
> 2. Обновляет или проверяет `CHANGELOG.md` для новой версии (все записи ведутся строго на английском языке).
> 3. Добавляет все файлы в индекс (`git add -A`).
> 4. Создаёт коммит (`git commit -m`).
> 5. Пушит изменения в главную ветку (`git push origin main`).
> 6. Создаёт тег версии (`git tag vX.Y.Z`) именно на этом новом коммите.
> 7. Пушит тег (`git push origin vX.Y.Z`), что в итоге триггерит GitHub Actions для релиза на PyPI.
>
> Если скрипт упадёт с ошибкой, используй эту логику, чтобы понять, на каком этапе произошёл сбой, и при необходимости заверши процесс вручную.

### Шаг 5: Подтвердить успех

После выполнения всех команд сообщи пользователю:
- Какая версия опубликована
- Что GitHub Actions запустится автоматически (можно проверить на вкладке Actions на GitHub)
- После успеха пакет появится на PyPI
- Если пользователь установил `ki-manager` через `uv tool` — потребуется запустить `uv tool install --reinstall ki-manager` для обновления пакета
- Предложи пользователю подготовить пост для LinkedIn:
  > «Хочешь сгенерировать готовый релизный пост для LinkedIn через скилл `linkedin-post`?»

## Правила ведения CHANGELOG.md

Файл `CHANGELOG.md` пишется для **конечных пользователей и AI-агентов**, а не для внутренней истории коммитов разработчиков:
1. **Язык**: Исключительно английский язык.
2. **Фокус на поведении и возможностях**: Формулировать записи на уровне MCP-инструментов, параметров конфигурации, CLI и видимых исправлений поведения (что изменилось для того, кто использует `ki-manager`).
3. **Чего НЕ должно быть в чейнджлоге**:
   - Внутренних путей к файлам реализации (`ki_utils.py`, `server.py` и т.д.).
   - Приватных имен функций и внутренних модулей.
   - Описания добавления или правок юнит-тестов (тесты — внутренняя деталь реализации).

## Common Mistakes

1. **Версии в `pyproject.toml` и `__init__.py` не совпадают** — PyPI отклонит пакет или загрузит неправильную версию.
2. **Тег создан на старом коммите** — `publish.yml` не окажется в истории этого коммита и GitHub Actions не запустится.
3. **Пакет не обновлён у пользователя** — после публикации пользователям нужно запустить `uv tool install --reinstall ki-manager`.
